5 · Real-Time Operating Systems (RTOS) & System Software

Everything in Section 3 was bare-metal — one main(), one while(1) loop, and interrupts. That's fine for a single LED. The moment a real product needs to juggle many independent responsibilities at once — reading a sensor every 10ms, running a control loop every 5ms, handling Bluetooth packets whenever they arrive, updating a display every 100ms — writing all of that by hand inside one giant loop becomes unmanageable. An RTOS is a small, extremely lightweight piece of software that gives you the illusion of many independent programs ("tasks") running at once, even on a single CPU core.

5.1 RTOS Core Concepts

Determinism vs Latency — the reason RTOS exists as its own category. A general-purpose OS (Windows, desktop Linux) optimizes for average throughput — fine if a task occasionally waits an extra 200ms. An RTOS optimizes for worst-case, guaranteed response time — if a control loop needs to run within 2ms of a sensor interrupt, the scheduler must guarantee that bound, every single time. This guarantee is determinism, and it's what "real-time" actually means — not "fast," but "predictable, bounded, and never missing a deadline."

Task States — the life cycle every RTOS task moves through

                     ┌──────────┐
        created ───► │  READY   │ ◄────────────┐
                     └────┬─────┘               │
                          │ scheduler picks      │ higher-priority
                          │ this task to run     │ task preempts,
                          ▼                      │ OR task's time
                     ┌──────────┐                │ slice ends
                     │ RUNNING  │────────────────┘
                     └────┬─────┘
                          │ task blocks on a
                          │ semaphore, delay,
                          │ or queue-wait
                          ▼
                     ┌──────────┐   event/timeout
                     │ BLOCKED  │───────────────► back to READY
                     └──────────┘
  • READY: eligible to run, waiting for the scheduler's turn.
  • RUNNING: actually executing on the CPU right now (only one task per core in this state).
  • BLOCKED: waiting on something — a timer delay, a semaphore, incoming queue data — and not competing for CPU time until that event occurs.

Context Switching — the mechanical trick that makes "multiple tasks on one CPU" possible. When the scheduler switches from Task A to Task B, it saves every CPU register Task A was using (including the Program Counter) onto Task A's private stack, then loads Task B's previously-saved registers from Task B's stack into the CPU. This is exactly why Section 3.1's PSP matters — each task gets its own private stack, and the RTOS just repoints PSP at a different task's stack to "switch." This save/restore takes a small, bounded number of cycles — RTOS designers work hard to keep this overhead small and predictable, since it can happen thousands of times per second.

5.2 Synchronization Primitives

The moment you have multiple tasks, you get a new bug category that doesn't exist in single-threaded bare-metal code: two tasks touching the same shared resource at the same time, in unpredictable order.

Race Condition — the core danger. Two tasks both doing counter++ on a shared variable: that single line is actually 3 CPU instructions — read, increment, write. If Task A is interrupted by Task B exactly between the read and write, Task B's entire increment can be silently lost. Worse, this bug is non-deterministic — it might not show up for millions of iterations, then appear once under specific timing, making it one of the hardest bug classes to reproduce.

Mutex (Mutual Exclusion lock) — solves this by ensuring only one task can hold the "lock" on a shared resource at a time. A task calls mutex_lock() before touching the resource and mutex_unlock() after; another task trying to lock an already-locked mutex simply blocks until release. A mutex has ownership — only the locking task can unlock it, which is what enables priority inheritance below.

Binary vs Counting Semaphores — semaphores solve signaling between tasks (or an ISR and a task), not protecting shared data.

  • Binary semaphore: a simple 0/1 flag. Classic use: an ISR "gives" it the instant a hardware event occurs (e.g. a UART byte fully received), and a task "taking" (blocked on) it wakes instantly to process — far more efficient than polling a status register in a loop.
  • Counting semaphore: like a binary semaphore but can exceed 1, acting as a resource counter (e.g. managing a pool of 4 DMA channels) — each take decrements, each give increments, and a task blocks only once the count hits zero.

A critical subtlety: unlike a mutex, a semaphore has no ownership — any task or ISR can "give" it, even one that never "took" it. This is exactly why semaphores are right for ISR-to-task signaling (an ISR should never use a mutex — mutex blocking logic is unsafe in interrupt context) while mutexes are right for protecting shared data between tasks.

Queues — the RTOS's built-in mechanism for safely passing actual data (not just a signal) between tasks, or from an ISR into a task. A fixed-size, RTOS-managed FIFO; queue_send() copies data in, queue_receive() copies data out, and the RTOS handles all internal locking so you never manually protect the queue's state.

Priority Inversion — the classic RTOS scheduling nightmare. Three tasks: Low, Medium, High priority. Low locks a mutex for a shared resource. High becomes ready and wants that same mutex, so it blocks on Low. Expected so far — but now Medium, which needs no shared resource at all, becomes ready. Since Medium outranks Low, the scheduler runs Medium instead of Low. Low never finishes to unlock the mutex, so High — the highest-priority task in the whole system — sits stuck behind a lower-priority task. This nearly doomed NASA's 1997 Mars Pathfinder mission (repeated watchdog resets, diagnosed and fixed remotely after landing).

Priority Inheritance — the standard fix. When a high-priority task blocks waiting for a mutex held by a lower-priority task, the RTOS temporarily boosts the lower-priority holder's priority up to match the waiting task — for exactly as long as it holds the mutex. This guarantees the holder can't be starved out by a medium-priority task in between, finishes quickly, and releases the mutex to the genuinely higher-priority task as fast as possible. Most production RTOSes (FreeRTOS, Zephyr, ThreadX) implement priority-inheritance mutexes as the default type specifically because of this failure mode.

5.3 Embedded Linux Fundamentals

For products with more computing demands than a microcontroller-class RTOS can comfortably handle — a camera feed, a full network stack, a graphical touchscreen UI — embedded Linux is the standard choice instead of (or alongside) an RTOS.

Bootloader (U-Boot) — the very first software that runs when power is applied, before Linux itself exists in memory. Its job: initialize the bare minimum hardware needed to read the Linux kernel image off storage (SD card, eMMC, SPI flash), load it into RAM, and jump execution into it. U-Boot also commonly provides an interactive serial-console shell for low-level recovery, firmware updates, and hardware bring-up debugging — often the first thing an embedded Linux engineer interacts with on brand-new custom hardware.

Linux Kernel — once U-Boot hands off control, the kernel initializes device drivers, memory management, process scheduling, and the filesystem, eventually launching the first user-space process (traditionally init, often systemd on modern embedded distributions).

Device Trees (.dts) — one of embedded Linux's most distinctive concepts. Unlike a desktop PC (which can dynamically discover most hardware via PCI/USB), an embedded board's layout — which I2C devices sit on which bus, which GPIO drives which chip-select, a sensor's interrupt line — is fixed and can't be auto-discovered. The Device Tree Source (.dts) is a plain-text description of the exact hardware layout, compiled into a binary Device Tree Blob (.dtb) loaded alongside the kernel at boot. This lets the same generic kernel binary support many different boards — only the .dtb changes, not the kernel.

// A tiny illustrative device tree fragment — declaring an I2C temperature
// sensor at address 0x48 on I2C bus 1
&i2c1 {
    status = "okay";
    temp_sensor@48 {
        compatible = "ti,tmp102";
        reg = <0x48>;             // the I2C address
        interrupt-parent = <&gpio1>;
        interrupts = <5 IRQ_TYPE_EDGE_FALLING>;  // which GPIO pin, which edge
    };
};

User Space vs Kernel Space — the fundamental security/stability boundary in any Linux system. Kernel space is where the OS core, drivers, and memory manager run, with full unrestricted hardware access. User space is where ordinary applications run, sandboxed with no direct hardware access — an application wanting to read a sensor must go through a system call into the kernel, which validates and performs the access on its behalf. This boundary is why a buggy user-space application can crash itself without taking down the whole device, while a bug in kernel-space code (a faulty driver) can crash or corrupt the entire system — exactly why driver code is held to a much higher standard of scrutiny than typical application code.
